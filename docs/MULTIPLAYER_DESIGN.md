## 1. 요구사항과 기본 결정

### 사용자가 요청한 사항

- 첫 화면을 **싱글 버전 / 대결 버전**으로 나눈다.
- 대결 버전에서는 방을 만들고 다른 유저가 그 방에 접속해 함께 플레이한다.
- 대결은 **키보드 정답 입력 방식만** 제공한다. 모바일 가상 키보드도 지원한다.
- 같은 문제에서 먼저 정답을 입력한 사람이 이긴다.
- 기존 인물 / 사물 / 인물·사물 섞기와 인물 세부 항목을 유지한다.
- 콘텐츠 보유 장수와 “정답이면 바로 다음 문제” 같은 설명은 화면에 표시하지 않는다.
- 이번 작업은 문서 작성만 한다. 구현과 배포는 후속 모델이 수행한다.

### 구현 기준으로 제안하는 기본값

| 항목 | 결정 |
| --- | --- |
| 이용 방식 | 회원가입 없이 닉네임과 초대 링크 또는 방 코드 |
| 방 인원 | 최소 2명, 최대 8명, 방장도 참가자로 포함 |
| 게임 길이 | 한 판 10문제, 문제당 5초 |
| 문제 승자 | 서버에 가장 먼저 도착한 유효 정답 제출자 한 명 |
| 득점 | 문제 승자 +1점, 나머지 0점, 오답 감점 없음 |
| 최종 승자 | 10문제 종료 시 최고 점수, 동점이면 공동 우승 |
| 전원 0점 | 우승자 없이 “이번 판은 정답자가 없어요” |
| 시작 | 모든 참가자가 준비하면 방장이 시작 |
| 중도 참가 | 게임 중 신규 참가 불가, 기존 참가자 재접속만 가능 |
| 다음 문제 | 정답/시간 초과 결과를 1.5초 보여준 후 자동 진행 |
| 방 공개 범위 | 초대 전용, 공개 방 목록·자동 매칭 없음 |

인원·문제 수·시간·결과 표시 시간은 서버 상수로 관리한다. 첫 버전에는 설정 UI를 늘리지 않는다.

## 2. 화면 및 사용자 흐름

### 첫 화면

```text
                 삼삼오오
       사진을 보고 이름을 맞혀보세요!

       [ 싱글 버전 ]  [ 대결 버전 ]

             효과음   사진 출처
```

여기에 인물/사물 카드, 입력 방식, 수량을 펼쳐 놓지 않는다.

### 싱글 버전

첫 화면 → 싱글 설정 → 게임 → 결과 → 다시 하기 또는 메인.

- 문제 버전: 인물 / 사물 / 인물·사물 섞기.
- 인물 선택 시에만 항목 드롭다운: 전체 / 국내 / 해외 / 만화·동화 캐릭터.
- 진행 방식: 직접 입력하기를 첫 번째·기본 선택으로, 같이 외치기를 두 번째로 유지.
- 기존 타이머, 입력 판정, 효과음, 출제 대기열, Enter 연속 진행을 유지.
- “싱글”은 온라인 방에 연결하지 않는 기존 모드의 진입점이다. 한 기기를 보고 여러 명이 외치는 방식도 이 안에 유지한다.

### 대결 진입

첫 화면 → 대결 → 닉네임 입력 → 방 만들기 또는 방 참가.

- 닉네임: 앞뒤 공백 제거 후 1~12 Unicode 코드 포인트, 제어 문자 금지.
- 방 안에서 동일 닉네임은 거절하고 다른 이름을 입력하도록 안내한다.
- 닉네임은 화면에 일반 텍스트로 렌더링한다.
- 방 코드는 혼동하기 쉬운 문자를 제외한 대문자·숫자 6자리. 생성 시 서버가 충돌을 검사한다.
- 링크 예: `/samsam/?room=ABC234`. 참가 전 닉네임을 입력한다.
- 링크에 접속 인증 토큰은 넣지 않는다.
- 방 만들기: 닉네임과 문제 버전/인물 항목을 설정하고 생성한다.
- 방 참가: 코드 입력 또는 초대 링크로 접속한다. 설정은 방장이 정한다.

### 대기실

```text
  ← 나가기           방 ABC234       [초대 링크 복사]
  인물 버전 · 전체 인물               [설정 변경: 방장]

  민수  방장  준비 완료
  지수        준비 완료
  준호        준비 중

  [준비 / 준비 취소]                  [게임 시작: 방장]
```

- 방장도 준비 버튼을 누른다. 연결된 참가자 2명 이상, 예약 중인 끊긴 참가자 없음, 전원 준비 상태일 때 시작 가능.
- 방장이 문제 설정을 바꾸거나 참가자가 추가/제거되면 전원 준비를 해제한다.
- 시작 요청과 참가 요청이 동시에 오면 서버에서 먼저 처리한 명령을 기준으로 판단한다.
- 시작 후 방 설정과 참가 명단을 해당 판에 고정한다.
- 방 코드는 참여용이며 사용자 인증 수단이 아니다.

### 대결 화면

```text
  인물 버전             3 / 10            [나가기] [소리]
  민수 2점       지수 0점       준호 0점
                        5
                  [문제 사진]
               [정답 입력           ] [제출]
```

- 사진, 남은 시간, 현재 문제 번호, 참가자 점수, 본인 표시가 중심이다.
- Enter 또는 제출 버튼으로 전송. 패스·정답 수동 처리·개인 일시정지 버튼은 없다.
- 정답 발생 즉시 전원 입력을 잠그고 `민수 정답! +1` 및 정답을 같은 화면에 표시한다.
- 오답은 제출자에게만 `다시 입력해 보세요`로 알리고 입력을 선택해 재입력 가능하게 한다.
- 다른 참가자의 오답 원문은 공개하지 않는다.
- 시간 초과는 `시간 종료`와 정답을 표시한다. 누구도 득점하지 않는다.
- 새 문제가 활성화되면 입력을 비우고 초점을 복원한다. 한글 조합 중 Enter는 전송하지 않는다(`isComposing` 및 조합 이벤트 처리).
- 한 번의 길게 누른 Enter가 반복 제출되지 않도록 한다. 느린 응답으로 이전 오답 안내가 새 문제에 나타나지 않게 라운드 ID를 확인한다.
- 모바일에서는 키보드가 사진·제출 버튼을 가리지 않도록 실제 화면 높이에 맞춘다.

### 결과

- 우승자 또는 공동 우승자, 전체 순위, 점수, 문제별 정답자 표시.
- 같은 점수는 같은 순위로 표시하며 접속 순서를 승패 기준으로 쓰지 않는다.
- 방장: `같은 방에서 한 판 더` → 대기실로 복귀, 점수와 준비 상태 초기화.
- 참가자: 방장의 다음 판 준비를 기다리거나 `메인으로` 나가기.
- 같은 방·같은 문제 설정의 다음 판에서는 기존 출제 대기열을 이어간다.

## 3. 게임 판정과 동기화

### 서버가 유일한 판정 주체

클라이언트는 제출 문자열과 현재 판/문제 ID만 전송한다. 정답 여부, 점수, 제한 시간, 승자, 다음 문제 선택은 모두 서버에서 결정한다. 브라우저가 보낸 점수나 “정답” 플래그를 신뢰하지 않는다.

1. 서버는 방별 명령을 직렬 처리한다.
2. 정답 제출 시 세션, 참가자, 판 ID, 문제 ID, 활성 상태, 마감 시각, 중복 요청을 검사한다.
3. 서버의 단조 증가 시계 기준 `opensAt <= receivedAt < deadline`에서만 제출을 허용한다.
4. 인정 답안에 일치하면 **문제 종료와 승자 기록, 점수 증가를 하나의 원자적 처리**로 수행한다.
5. 이후 제출은 `ROUND_CLOSED`. 타이머 콜백과 제출이 경쟁해도 승자와 점수는 한 번만 기록한다.
6. 서버 단조 시계로 측정한 처리 순서를 따른다. 클라이언트 전송 시각은 판정에 사용하지 않는다.

네트워크 지연이 있는 만큼 물리적으로 먼저 키를 누른 사람까지 보장하지 않는다. 판정 기준은 “서버에 먼저 도착한 정답”이며, 방 규칙 도움말에서 짧게 안내한다. 고의로 지연값을 조작할 수 있는 클라이언트 시각 보정 점수는 도입하지 않는다.

### 정답 정규화

기존 `dist/app.js`의 NFKC 정규화, 소문자화, 공백·가운데점·마침표·밑줄·하이픈 제거 규칙을 기준으로 서버의 공용 함수에 옮긴다. `answer` 또는 `accepted`와 정규화 후 완전 일치할 때만 정답이다. 부분 문자열·추측 기반 유사 정답은 인정하지 않는다. 빈 입력은 전송하지 않으며 서버에서도 거절한다.

### 문제 준비와 시작

- 판 시작 시 `COUNTDOWN`으로 전환해 전원에게 3초 시작 카운트다운을 보여준다.
- 각 문제는 `PREPARING → ACTIVE → REVEAL` 순서로 진행한다.
- PREPARING에서 사진 주소와 불투명한 `roundId`를 전송한다. 전원은 사진을 화면에 숨긴 채 내려받고 디코딩 후 `round.ready`를 보낸다.
- 전원이 준비하면 서버가 약 1초 뒤의 `opensAt`과 `deadline=opensAt+5000ms`를 공지한다. 브라우저는 그 시각에 사진을 보여준다.
- 서버는 단조 시계로 마감을 관리하고 클라이언트 표시용 epoch 시각을 함께 보낸다. ping 왕복 중간값 기반 시계 오프셋을 갱신한다. 화면 타이머가 어긋나도 서버 판정이 우선이다.
- 준비 제한 8초. 하나라도 사진 실패/준비 미완료이면 그 문제는 득점·문제 수 차감 없이 전원 건너뛴다. 연속 3회 실패하면 판을 취소하고 대기실로 돌아가 연결 확인 메시지를 보여준다.
- 사진 준비 중에는 정답을 받을 수 없다. 예약된 오래된 타이머는 `matchId`와 `roundId`가 바뀌면 무효화한다.
- 모든 클라이언트가 정확히 같은 순간 사진을 보는 것은 네트워크와 기기 성능 때문에 보장하지 못한다. 이 방식은 일반적인 친구 간 대결의 표시 차이를 줄이기 위한 것이다.

### 무작위 출제

서버가 `reviewed: true` 데이터만 선택한다. 인물 전체는 korean/global/character의 합집합, 혼합은 그 집합과 object의 합집합이다. ID로 중복 제거한다. 방·문제 설정별로 셔플 대기열을 유지하고 한 판 안의 중복은 금지한다. 설정별 남은 문제를 소진하면 다시 섞되 직전 문제를 즉시 재출제하지 않는다. 유효 사진이 부족해 10문제를 구성할 수 없으면 시작을 거절한다.

## 4. 방 상태와 예외 처리

```text
LOBBY → COUNTDOWN → PREPARING → ACTIVE → REVEAL
                         ↑                   │
                         └── 다음 문제 ──────┘
                                      마지막 문제 → FINISHED → LOBBY
모든 상태 → CLOSED (방 만료/참가자 없음/운영 종료)
```

| 상황 | 처리 |
| --- | --- |
| 새로고침·일시 끊김 | 30초 동안 자리와 점수 유지. 동일 세션으로 재접속하면 전체 상태 재전송 |
| 대기실에서 끊김 | 준비 해제, 재접속 대기 중 시작 불가. 30초 후 자리 제거 |
| 플레이 중 끊김 | 게임과 시계는 계속 진행, 재접속 전에는 제출 불가 |
| 플레이 중 접속자 1명 이하 | 현재 문제를 무효 종료하고 판 취소, 대기실로 복귀. 자동 승리 부여 없음 |
| 방장 명시적 퇴장 | 가장 먼저 들어온 연결된 참가자에게 즉시 방장 이전 |
| 방장 연결 끊김 | 30초 유예 후 연결된 참가자에게 방장 이전. 진행 중 판은 서버가 계속 진행 |
| 중도 명시적 퇴장 | 해당 판 재참가 불가. 과거 득점과 문제 승자는 기록에 보존하되 최종 우승 대상에서는 제외 |
| 같은 세션의 새 탭 접속 | 새 연결을 활성 연결로 삼고 기존 연결에는 다른 탭 연결 안내 후 입력 차단 |
| 만원·없는 방·게임 중 입장 | 각각 독립된 안내 메시지. 메인으로 돌아가거나 코드 재입력 가능 |
| 뒤로가기 | 참가 중에는 나가기 확인. 링크 공유/새로고침은 새 참가자로 만들지 않음 |
| 전원 끊김 | 재접속 유예 동안 방 유지. 활성 판은 취소하고 대기실, 유예 종료 후 방 삭제 |
| 비어 있는 방 | 마지막 자리 제거 시 삭제 |
| 대기실·결과에서 30분 무활동 | 만료 1분 전 알림 후 방 닫기. 자동 ping은 사용자 활동으로 세지 않음 |
| 서버 재시작 | 초기 버전은 방 복구 미지원. 재접속 시 “방이 종료됐어요”로 안내 |

재접속으로 이미 끝난 문제에 답할 수 없다. 진행 중 문제라면 최신 사진과 남은 시간만 복원하고 타이머를 새로 시작하지 않는다. 연결 유예와 슬롯 관리도 서버가 수행한다.

## 5. 기존 코드에 맞춘 구성

현재 확인한 구조:

- `dist/index.html`, `dist/app.js`, `dist/style.css`: 정적 클라이언트.
- `dist/assets/questions.json`: 정답·인정 답안·사진·출처가 함께 있는 공개 JSON.
- `Dockerfile`, `nginx.conf`: 정적 파일 제공 Nginx.
- `k8s/samsam.yaml`: namespace `samsam`, web 1 replica, NodePort 31083.
- `infra/nginx/samsam-location.conf`: 공개 `/samsam/` 경로를 내부 31083으로 전달.

### 제안 구조

```text
브라우저
  └─ HTTPS /samsam/
      └─ 기존 외부 Nginx
          └─ 기존 web Nginx (31083)
              ├─ /             정적 클라이언트·사진
              ├─ /api/         room-server ClusterIP
              └─ /socket.io/   room-server ClusterIP (WebSocket upgrade)

room-server: Node.js + TypeScript + Socket.IO, 단일 프로세스·단일 replica
  ├─ 방·참가자 세션·게임 상태 (메모리)
  ├─ 정답 판정 / 출제 / 시계
  └─ 서버 전용 문제 데이터
```

이는 구현 기술 제안이다. 구현 모델은 착수 시 호환되는 유지보수 버전을 확인하고 lockfile에 고정한다. 첫 버전에는 계정 DB, 영구 랭킹, Redis를 추가하지 않는다. 메모리 상태이므로 재시작하면 방이 종료되는 한계를 UI와 운영 문서에 명시한다.

권장 파일 분리:

- `dist/js/navigation.js`: 메인/싱글/대결 화면 전환.
- `dist/js/single-game.js`: 기존 싱글 로직 분리.
- `dist/js/battle-client.js`: 방 UI·소켓·재접속·표시 타이머.
- `server/src/rooms/`: 방·세션 수명 관리.
- `server/src/game/`: 상태 전이·문제 순서·정답 판정.
- `server/src/protocol/`: 입력 검증과 이벤트 타입.
- `server/data/questions.json`: 서버가 판정하는 콘텐츠 원본.
- `server/test/`: 판정 경쟁, 재접속, 상태 전이 테스트.

싱글 화면에 온라인 연결 오류가 영향을 주지 않도록 화면/상태를 분리한다. 온라인 게임 실행 중에 기존 싱글 `keydown` 및 `visibilitychange` 핸들러가 개입하지 않게 정리한다.

## 6. 데이터와 통신 계약

### 서버 내부 데이터

| 구조 | 필수 값 |
| --- | --- |
| Room | internalId, code, hostPlayerId, state, settings, players, match, questionQueues, version, lastUserActivityAt |
| Player | id, nickname, sessionTokenHash, connectionId, joinedAt, connected, disconnectedAt, ready, leftMatch |
| Match | id, participantIds, scores, roundIndex, targetRounds, round, results |
| Round | id, privateQuestionId, state, opensAt, deadline, winnerPlayerId, readyPlayerIds, imageToken |
| Session | 불투명 난수 token, playerId, roomId, expiresAt |

`privateQuestionId`, 정답 목록, 토큰 해시, 다음 문제 순서는 공개 상태에 넣지 않는다. Room.version은 상태 변경마다 단조 증가한다.

### HTTP

공개 기준 prefix는 `/samsam/api`이며 내부 서버는 `/api`로 받도록 프록시에서 정한다.

- `POST /rooms`: `{nickname, settings}` → `{code, playerId, sessionToken, snapshot}`.
- `POST /rooms/:code/join`: `{nickname}` → 동일한 응답. 진행 중 신규 참가를 거절한다.
- `GET /health/live`, `GET /health/ready`: 프로세스/콘텐츠 로딩 준비 상태 확인. 외부 공개는 필요 없음.

생성·참가 요청에는 idempotency key를 사용해 네트워크 재시도 시 방/플레이어가 중복 생성되지 않게 한다. 세션 토큰은 URL과 로그에 남기지 않고 브라우저 sessionStorage에 방별 저장한다. 복구 시 소켓 인증 필드로 보낸다. 인증 실패 토큰은 폐기하고 참가 화면으로 복귀한다.

### 소켓 이벤트

공개 연결 path `/samsam/socket.io/`, 내부 path `/socket.io/`. Socket.IO와 일반 WebSocket을 섞어 구현하지 않는다.

공통 명령: `{requestId, roomCode, ...payload}`. 답 제출은 `{requestId, matchId, roundId, answer}`. 사용자 ID는 연결 세션에서 결정한다.

| 방향 | 이벤트 | 내용 |
| --- | --- | --- |
| client → server | room.sync | 현재 snapshot 요청 |
| client → server | player.ready | 준비 여부 |
| client → server | room.settings | 방장만 설정 변경, LOBBY만 허용 |
| client → server | match.start | 방장만 시작, 전원 준비 조건 검사 |
| client → server | round.ready | 사진 decode 완료, matchId/roundId 포함 |
| client → server | round.assetFailed | 사진 로딩 실패 보고 |
| client → server | answer.submit | 현재 문제 답안 |
| client → server | match.rematch | FINISHED에서 방장만 LOBBY 복귀 |
| client → server | room.leave | 명시적 퇴장 |
| server → client | room.snapshot | version, serverNow, 공개 방/판/현재 문제 상태 |
| server → client | match.countdown | 시작 예정 시각 |
| server → client | round.prepare | roundId, 이미지 URL, 준비 마감 |
| server → client | round.open | opensAt, deadline, roundIndex |
| server → client | answer.result | 요청자에게만 wrong/accepted/rejected, requestId/roundId |
| server → client | round.resolved | 승자 또는 timeout, 정답, 점수, 다음 전환 시각 |
| server → client | match.finished | 최종 점수, 공동 순위, 우승자 목록 |
| server → client | room.closed / session.replaced | 종료 이유와 복귀 안내 |

모든 변경 이벤트에 matchId/roundId(해당 시), version, serverNow를 포함한다. 늦은 구버전 이벤트는 무시한다. 버전이 건너뛰면 snapshot으로 동기화하며 snapshot이 최종 기준이다. reconnect는 반드시 snapshot을 받아 입력 가능 여부를 재판단한다. snapshot은 PREPARING의 사진, ACTIVE의 현재 문제·마감, REVEAL의 공개 정답, FINISHED의 결과를 각각 복원할 수 있어야 한다.

`requestId`별 처리 결과는 해당 세션에서 5분간 제한된 크기로 보관한다. 중복 제출에 점수를 다시 주지 않는다. 오류 코드는 ROOM_NOT_FOUND, ROOM_FULL, MATCH_IN_PROGRESS, NOT_HOST, NOT_READY, INVALID_SESSION, STALE_ROUND, ROUND_NOT_OPEN, ROUND_CLOSED, RATE_LIMITED, INVALID_INPUT 등으로 고정하고 UI 문구와 분리한다.

## 7. 공개 데이터와 공정성 범위

현재 공개 `questions.json`에는 정답이 있고 사진 출처에서도 인물 이름을 알 수 있다. 클라이언트에 보내는 새 이벤트에서 answer만 지운다고 부정행위가 해결되는 것은 아니다.

첫 버전은 **친구 간 초대 대결**을 대상으로 한다. 서버 판정으로 점수 조작과 중복 승자를 막되 기존 공개 사진·정답을 미리 수집하는 행위까지 차단한다고 주장하지 않는다. 공개 순위나 금전 보상은 제공하지 않는다.

- 대결 클라이언트에서는 전체 정답 JSON을 요청하지 않는다. 서버 전용 데이터로 판정한다.
- 현재 문제에는 불투명한 roundId와 임시 이미지 URL만 제공하고 미래 문제·정답·파일 이름 힌트를 보내지 않는다.
- 이미지 URL을 복잡하게 만드는 것은 완전한 부정행위 방지가 아니다. 싱글의 동일 이미지/공개 출처와 대조할 수 있는 한계를 유지보수 문서에 기록한다.
- 정답은 REVEAL에서만 이벤트에 포함한다.
- 기존 사진 크레딧과 라이선스 표시는 유지한다. 이름을 감추려는 목적으로 필요한 저작자 표기를 삭제하지 않는다.
- 향후 엄격한 경쟁 모드를 원하면 싱글 공개 데이터와 분리된 대결 콘텐츠, 별도 제공 방식, 남용 방지 정책을 다시 설계한다.

## 8. 입력 보호 및 운영 한도

- 모든 HTTP/소켓 입력을 스키마 검증. 답안 30 코드 포인트, 이벤트 크기 2KB 이내.
- 제출은 플레이어별 초당 3회(짧은 burst 3회), 과도한 입력에는 재시도 대기 표시.
- 방 코드 추측과 생성 남용을 막기 위해 생성 IP당 분당 5회, 참가 시도 IP당 분당 30회를 초기값으로 설정.
- 전체 방 100개, 방별 8명 상한으로 시작. 상한 초과는 사용자에게 서버 혼잡 안내.
- IP 한도는 공유 네트워크 이용자를 고려해 환경 설정 가능하게 한다. 신뢰하는 프록시에서 받은 IP만 사용한다.
- 소켓 Origin은 운영 origin 및 명시적 개발 origin만 허용. 세션마다 권한을 확인한다.
- 닉네임·정답 입력을 innerHTML로 출력하지 않는다.
- 연결 수, 방 수, 판정 지연, 이미지 실패, 끊김, 오류를 측정한다. 토큰·답안 원문을 일반 로그에 남기지 않는다.

## 9. Kubernetes 배포 설계

실제 배포는 후속 구현 작업 범위다. 현재 NodePort 주소를 사용자에게 새 접속 주소로 제시하지 않는다.

1. 기존 web Service와 공개 `/samsam/` 경로를 유지한다.
2. namespace samsam에 room-server Deployment와 ClusterIP Service를 추가한다.
3. 초기 replica는 **1**, 프로세스도 1개로 고정한다. 여러 replica에 메모리 방을 나누면 판정과 연결이 깨진다.
4. 초기 API 자원은 CPU request 100m / limit 500m, memory request 128Mi / limit 256Mi부터 부하 측정 후 조정한다.
5. 서버의 liveness/readiness probe와 SIGTERM 처리를 구현한다. 종료 신호 시 신규 방/참가를 막고 연결된 사용자에게 종료 안내 후 닫는다.
6. 배포 전략은 Recreate로 설정해 서로 다른 메모리 방 서버가 동시에 서비스되는 상황을 피한다. 배포 시 진행 중 방은 종료되므로 운영자는 활성 방 수를 먼저 확인한다.
7. 외부 Nginx와 web Nginx **두 구간 모두** Upgrade/Connection 헤더, HTTP/1.1, 적절한 idle timeout을 설정한다. 프록시 timeout은 socket heartbeat 시간보다 길게 둔다.
8. `/samsam/api/`와 `/samsam/socket.io/`의 접두사 제거를 명시적으로 맞추고 외부 HTTPS에서 실제 연결을 검사한다. LAN 주소 테스트만으로 완료 처리하지 않는다.
9. Nginx CSP의 connect-src가 실제 운영 WSS origin을 허용하는지 확인한다. 필요하면 정확한 WSS origin을 추가한다.
10. 서버와 클라이언트 protocolVersion 불일치 시 새로고침 안내. 정적 JS는 콘텐츠 해시 또는 버전으로 캐시를 갱신한다.
11. client/server 이미지를 별도 태그로 관리하며 manifest와 배포 스크립트를 함께 갱신한다. 롤백 시 두 버전의 호환성을 확인한다.

DB·Redis를 통한 상태 복구와 다중 replica는 후속 확장이다. Socket.IO adapter만 추가하는 것으로 원자적 승자 판정이나 게임 상태 공유가 해결되지는 않는다.

## 10. 구현 순서와 인수 기준

### 권장 구현 순서

1. 화면 진입점을 싱글/대결로 분리하고 기존 싱글 회귀 확인.
2. 서버 공용 타입, 문제 로더, 정규화 함수, 방 상태 머신 구현.
3. 생성/참가/준비/설정/방장 이전/세션 재접속 구현.
4. 문제 준비, 5초 타이머, 원자적 정답 판정, 점수 및 결과 구현.
5. 모바일 입력·한글 조합·초점 복원과 예외 UI 구현.
6. 프록시와 Kubernetes 구성 후 공개 주소에서 다중 기기 검증.
7. 구현 결과와 실제 테스트 증거를 별도 문서로 기록하고 운영 반영.

### 반드시 확인할 시나리오

- 처음에는 싱글/대결 두 선택만 나오고, 기존 싱글 두 방식이 정상 동작한다.
- 대결에는 직접 입력만 있고 인물 세부 항목, 사물, 혼합 설정이 서버 출제에 반영된다.
- 서로 다른 브라우저 세션 및 다른 기기에서 초대 링크/코드로 같은 방에 들어간다.
- 2명 및 8명에서 준비/시작, 같은 사진·문제 번호, 점수·결과가 일치한다.
- 거의 동시에 정답 2개를 보내도 승자는 한 명, 점수는 정확히 1점만 증가한다.
- 중복 requestId, 이전 문제 답안, 종료 직후 답안, 마감 경계값 제출이 잘못 득점하지 않는다. 가짜 시계를 주입한 서버 테스트로 경계를 재현한다.
- 오답 후 재입력, 한글 조합 중 Enter, 빠른 연타, 10번째 문제 종료가 정상이다.
- 사진 실패/준비 타임아웃은 전체 참가자에게 같은 전환을 만들며 점수·문제 수가 어긋나지 않는다.
- 끊긴 참가자 재접속, 새로고침, 다른 탭 연결, 방장 퇴장, 한 명 남음, 방 만료가 규칙대로 처리된다.
- 만원 방, 잘못된 코드, 진행 중 입장, 권한 없는 시작·설정 변경, 가짜 사용자 ID를 거절한다.
- 정답이 없는 판, 공동 우승, 같은 방 재경기와 출제 대기열이 동작한다.
- 스마트폰에서 사진과 입력/제출이 가려지지 않고 다음 문제 입력을 이어갈 수 있다.
- 외부 HTTPS 주소에서 WebSocket 업그레이드와 heartbeat가 유지된다.
- 서버 재시작/배포로 방이 종료되면 무한 재접속·멈춘 게임 대신 안내가 표시된다.
- 목표 부하 100방×8연결에서 CPU/메모리, 이벤트 처리 지연을 기록하고 실제 수용 가능 한도를 설정한다.

## 11. 후속 구현 모델에게 전달할 작업 지시

> docs/MULTIPLAYER_DESIGN.md를 기준으로 삼삼오오 메인을 싱글/대결로 나누고 방 기반 실시간 대결을 구현해라. 기존 싱글 기능과 공개 /samsam/ 경로를 유지해라. 대결은 키보드 입력 전용이며 서버가 같은 문제와 마감 시각을 관리하고 첫 유효 정답에만 1점을 부여해야 한다. 방 생성·초대·준비·재접속·방장 이전·공동 우승까지 구현하고, 동시 제출의 중복 득점 방지와 외부 주소의 다중 기기 동작을 검증해라. 콘텐츠 장수와 불필요한 동작 설명은 화면에 추가하지 마라. 배포 시 메모리 방 종료와 기존 싱글 회귀를 확인하고 결과를 보고해라.
